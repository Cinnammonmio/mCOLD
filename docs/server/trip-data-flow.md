# mCOLD — ข้อมูล trip ไปไหนบ้าง

ตกลงกันเมื่อ 5 ต.ค. 2026: ระหว่าง trip เก็บทุกแถวไว้ในเครื่อง ส่งขึ้น server แค่ `status`
ส่วนข้อมูลทั้ง trip ส่งหลังจบ trip ทางแอป (BLE) หรือทาง Wi-Fi ของกล่องเอง
รูปแบบแถวอยู่ที่ [`server-mqtt-brief.md`](server-mqtt-brief.md) ข้อ 3
และ topic ทั้งหมดอยู่ที่ [`mqtt-topics.md`](mqtt-topics.md)

## Flow

```
เริ่ม trip (แตะ NFC + แอป)
  │  ทุกแถว (SAMPLE, ALARM, USB, ...) เก็บลงเครื่อง
  │  MQTT: ส่งแค่ status ทุกรอบ upload_period_s (5 นาที) และทันทีเมื่อมีเน็ต
  ▼
จบ trip (ในแอปเท่านั้น — กล่องไม่มีปุ่ม) → trip สถานะ "รอส่ง"
  │
  ├─ [จบ trip] ──────────────────────────────┐
  │                                           ▼
  │                         เจอ Wi-Fi → ทยอยส่งทาง MQTT ก้อนละ 20 แถว
  │                         trip เก่าก่อน · ต่อจากก้อนที่ค้าง · server ตอบ ACK ทุกก้อน
  │                         ครบ → "ส่งแล้ว"
  │
  └─ [จบ trip และส่งข้อมูล]
        แอปดึงทั้ง trip ผ่าน BLE (READ_LOG_CHUNK) → สร้างไฟล์ CSV
        แอปส่งไฟล์ขึ้น server เอง
          สำเร็จ → แอปเรียก MARK_DELIVERED → "ส่งแล้ว" (กล่องไม่ส่งทาง Wi-Fi)
          ไม่สำเร็จ → กล่องยัง "รอส่ง" แล้วส่งทาง Wi-Fi เองภายหลัง
  ▼
trip "ส่งแล้ว" ยังอยู่ในเครื่อง และถูกลบก่อนเมื่อพื้นที่เต็ม
```

## สถานะของ trip ในเครื่อง

| สถานะ | ความหมาย | ดูได้จาก |
|---|---|---|
| กำลังรัน | ยังเก็บแถวอยู่ ไม่ส่งแถวขึ้น server | `status` → `trip.active` |
| รอส่ง | จบแล้ว server ยังไม่ได้ครบ | `LIST_TRIPS` → `"sent": false` · หน้าจอสรุป "NOT SENT" |
| ส่งแล้ว | server ได้ครบ (ACK ครบ หรือแอปบอก) | `"sent": true` · หน้าจอสรุป "SENT" |

## ระหว่าง trip ไม่มีเน็ต

- แถวไม่หาย ทุกแถวอยู่ในเครื่อง
- alarm ยังเตือนที่ตัวกล่อง (LED, จอ, เสียง)
- server เห็น `status` ล่าสุดค้างไว้ (retain) พร้อมเวลา จึงรู้ว่ากล่องหายไปนานเท่าไร
- พอมีเน็ต กล่องส่ง `status` ทันที ใน `trip` มี `alarms_raised` (จำนวน alarm ทั้ง trip)
  และ `last_alarm` (ชนิด + เวลา) server จึงรู้ว่ามี alarm เกิดตอนออฟไลน์ แม้ตอนนี้หายแล้ว
- รายละเอียดทุกแถวขึ้น server ตอนส่ง trip หลังจบ

## ส่งทาง Wi-Fi (MQTT)

`mcold/<sn>/rec` — ก้อนละ 20 แถว เฉพาะ trip ที่จบแล้ว

```json
{"sn":"mCDV1-L0169-1069-002","trip_id":"95518e06-1b3b-494f-b4c5-284ae94f5424","trip_date":"20261007","trip_number":2,"part":2,"parts":6,
 "from":20,"to":39,"last":false,"rows":[ ...20 แถว... ]}
```

- `part` / `parts`: ก้อนที่เท่าไรจากทั้งหมด ก้อนที่ k มีแถว `seq` 20(k−1) … 20k−1 เสมอ
- `last: true` ที่ก้อนสุดท้าย (มี `TRIP_STOP` อยู่ในนั้น)
- server ตอบ `mcold/v1/<sn>/ack` → `{"trip_id":"95518e06-1b3b-494f-b4c5-284ae94f5424","upto":39}` หลังเก็บก้อนนั้นแล้ว
- ไม่ได้ ACK → กล่องส่งก้อนเดิมซ้ำ (เว้นนานขึ้นเรื่อยๆ) **server ต้องตอบ ACK เสมอ**
- ตอนใช้แบต แต่ละรอบส่งได้ราว 45 วินาที ที่เหลือส่งต่อรอบถัดไป
- ขนาด: แถว JSON ละ ~350 byte → ก้อนละ ~9 KB · trip 10 วัน ≈ 2,900 แถว ≈ 145 ก้อน ≈ 1 MB

## ส่งทางแอป (BLE)

1. แอปเรียก `STOP_TRIP` (ปุ่ม "จบ trip และส่งข้อมูล")
2. แอปอ่านทั้ง trip ด้วย `READ_LOG_CHUNK` (ทีละ 16 แถว แบบ binary 32 byte/แถว เร็วกว่า CSV ~5 เท่า)
3. แอปแปลงเป็น CSV column เดียวกับที่ server ได้ ชื่อไฟล์ `TRIP_<SN>_<YYMMDDhhmm>.csv`
   เช่น `TRIP_mCDV1-L0169-1069-001_2610050330.csv` (SN เต็มตามฉลาก + เวลาเริ่ม trip)
4. แอปส่งไฟล์ขึ้น server
5. server ตอบว่าเก็บแล้ว → แอปเรียก `MARK_DELIVERED {"trip_id":"<uuid>"}` (ต้อง authorize แล้ว)
   กล่องจะไม่ส่ง trip นี้ทาง Wi-Fi อีก

## งานแต่ละฝ่าย

| ฝ่าย | ต้องทำ |
|---|---|
| firmware | ✅ เสร็จใน 0.7.0-dev.5 |
| server | subscribe `mcold/+/rec` · ประกอบ trip จาก `part` · ตอบ ACK ทุกก้อน · กรองซ้ำด้วย (trip_id, seq) · รับไฟล์ CSV จากแอป · ดู `status` ระหว่าง trip |
| แอป | ปุ่ม "จบ trip" และ "จบ trip และส่งข้อมูล" · ดึง trip ผ่าน BLE · สร้าง CSV · ส่งขึ้น server · เรียก `MARK_DELIVERED` |
