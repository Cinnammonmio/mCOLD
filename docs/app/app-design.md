# mCOLD — การออกแบบแอป (ส่งต่อทีมทำแอป)

เอกสารนี้สรุปหน้าจอ ลำดับการใช้งาน และพฤติกรรมของแอปที่ตกลงแล้วจาก demo
ใช้คู่กับ [`ble-protocol.md`](ble-protocol.md) (คำสั่ง BLE), [`device-settings.md`](device-settings.md) (ค่าตั้ง)
และ [`../server/trip-data-flow.md`](../server/trip-data-flow.md) (ข้อมูล trip ไปไหน)

## Demo

|---|---|
| ไฟล์ demo | [`demo/index.html`](demo/index.html) ไฟล์เดียว เปิดในเบราว์เซอร์ได้เลย (ไม่ต้องมี server) |
| โค้ด demo | [`../../app-demo/`](../../app-demo/README.md) React + Vite · `npm install` แล้ว `npm run build` สร้าง `docs/app/demo/index.html` ใหม่ |
| คู่มือใน demo | เปิด `demo/index.html#guide` หรือปุ่ม "คู่มือสำหรับทีมพัฒนา" ในแผงควบคุมเดโม: ตารางหน้าจอ, mapping คำสั่ง, ที่มาของข้อมูล, สถานการณ์ทดสอบ |

Demo ใช้ข้อมูลจำลองทั้งหมด ไม่เรียก Bluetooth, NFC หรือ server จริง แผง **ควบคุมเดโม** (ขวามือบน Desktop หรือปุ่ม "เดโม" บนมือถือ)
จำลอง BLE หลุด, ไม่มีอินเทอร์เน็ต, server ล้มเหลว, อุณหภูมิเกินช่วง, ไม่พบหัววัด, แบตต่ำ และรีเซ็ตข้อมูล
ส่วนที่มีกรอบสีม่วงประในแอปคือปุ่มจำลอง ไม่ใช่ส่วนของแอปจริง

## 1. หลักการที่ตกลงแล้ว

1. **แอปเดียวหลายผลิตภัณฑ์** ชื่อแอปชั่วคราว "Cold Chain Hub" เปิดแอปแล้วเข้าหน้าเลือกผลิตภัณฑ์ทันที (eTEMP, mCOLD, SMT) แสดงแค่ชื่อ ไม่มีคำอธิบาย ส่วน eTEMP และ SMT ยังเป็นหน้า "อยู่ระหว่างพัฒนา"
2. **เครื่อง mCOLD ผูกกับวอร์ดของลูกค้า** ผู้ใช้ทุกคนในวอร์ดใช้เครื่องของวอร์ดร่วมกัน แอปแสดงเฉพาะเครื่องของวอร์ดผู้ใช้ และไม่ให้ใช้เครื่องของวอร์ดอื่น
3. **เครื่องไม่ผูกกับกล่องยา** ย้ายไปติดกล่องไหนก็ได้ทุกทริป จึงตั้งชื่อเครื่องตามหมายเลข (`mCOLD 001` = 3 หลักท้ายของ SN) และเก็บ "กล่องหรือสินค้าที่ติด" เป็นข้อมูลของทริป
4. **แอปบันทึกว่าใครทำอะไร** ผู้เริ่มทริป, ผู้จบทริป, ผู้รับทราบการแจ้งเตือน, ผู้ส่งข้อมูล, ผู้แก้ค่าตั้งล่าสุด (กล่องไม่รู้จักผู้ใช้ ข้อมูลนี้เป็นของแอป/server ผูกกับ `trip_id`)
5. **เมนูของเครื่องแสดงเมื่อเชื่อมต่อแล้วเท่านั้น** รายการเครื่อง → แตะ NFC → เมนู 3 อย่าง: เริ่ม / จบทริป, ตั้งค่าอุปกรณ์, ส่งข้อมูล ถ้าหลุดการเชื่อมต่อ เมนูซ่อนและมีปุ่มเชื่อมต่อใหม่
6. **เส้นทางส่งข้อมูลหลักคือผ่านแอป**: กล่อง → BLE → แอป → อินเทอร์เน็ตมือถือ → server
7. **ข้อมูลที่ไม่สดต้องบอกว่าไม่สด** ไม่ได้เชื่อมต่อ = "ข้อมูลล่าสุดที่ได้รับ HH:MM" ตัวเลขสีเทา · ค่าที่ไม่รู้แสดง "—" ไม่ใช่ 0
8. **แยกสถานะ 4 อย่างเสมอ**: BLE เชื่อมอยู่ไหม · มือถือมีอินเทอร์เน็ตไหม · ทริปกำลังบันทึกหรือจบแล้ว · ข้อมูลถึง server แล้วหรือยัง
9. **หน้าผู้ใช้ไม่แสดงชื่อคำสั่ง, UUID หรือ `trip_id`** ทริปแสดงเป็น "ทริปที่ N · วันที่" จาก `trip_number` และ `trip_date`

## 2. หน้าจอ

```
เลือกผลิตภัณฑ์ ──┬── eTEMP / SMT (อยู่ระหว่างพัฒนา)
                 └── mCOLD: รายการเครื่องของวอร์ด
                       ├── แตะ NFC เพื่อเชื่อมต่อ ──► เมนูของเครื่อง
                       │                              ├── เริ่ม / จบทริป ── ฟอร์มเริ่มทริปหน้าเดียว / ระหว่างทริป ── จบทริป
                       │                              ├── ตั้งค่าอุปกรณ์ ── Wi-Fi ช่อง 1–5
                       │                              └── ส่งข้อมูล ── ความคืบหน้า 5 ขั้น
                       └── เริ่มทริปหลายเครื่อง
```

### 2.1 เลือกผลิตภัณฑ์
การ์ด 3 ใบ ไอคอน + ชื่อ · มุมขวาบนแสดงผู้ใช้ปัจจุบัน (แตะเพื่อดูวอร์ด/สลับผู้ใช้)

### 2.2 mCOLD: รายการเครื่อง
- แถบวอร์ดและผู้ใช้ ("หอผู้ป่วยอายุรกรรม 3 · สมชาย ใจดี · พยาบาล")
- ถ้ามีเครื่องเชื่อมอยู่: การ์ด "เชื่อมต่ออยู่ · แตะเพื่อเปิดเมนู"
- ปุ่ม **แตะ NFC เพื่อเชื่อมต่อ** และ **เริ่มทริปหลายเครื่อง**
- ตัวกรอง ทั้งหมด / กำลังบันทึก n / รอส่ง n
- การ์ดเครื่อง: ชื่อ, SN, อุณหภูมิ, แบต %, กล่องที่ติด, เริ่มโดย, ชิปสถานะ (เชื่อมต่อ / ว่างหรือกำลังบันทึก / รอส่ง n), "ข้อมูลล่าสุดที่ได้รับ HH:MM"
- แตะการ์ด = เชื่อมต่อเครื่องนั้น

ค่าบนการ์ดเป็น**ค่าที่มือถือเครื่องนั้นได้รับตอนเชื่อมต่อครั้งล่าสุด** (ดูข้อ 4) ถ้าต้องการค่าสดทุกเครื่องต้องมี API จาก server

### 2.3 เชื่อมต่อ (sheet)
ขั้น: แตะ NFC → พบอุปกรณ์ → เชื่อมต่อ Bluetooth → ยืนยันสิทธิ์ → พร้อมสั่งงาน แต่ละขั้นที่ผ่านแสดงข้อมูลที่ได้:

| ขั้น | แสดง |
|---|---|
| แตะ NFC | หมายเลขเครื่อง, Bluetooth MAC, "รหัสยืนยัน: ได้รับแล้ว (ไม่แสดง)" — **ห้ามแสดง `key`** |
| พบอุปกรณ์ | ชื่อที่ประกาศ (= SN) |
| เชื่อมต่อ Bluetooth | Firmware, ฮาร์ดแวร์, โปรโตคอล (จาก INFO) |
| ยืนยันสิทธิ์ | ยืนยันแล้ว |

ผ่านครบแล้ว sheet ปิดเองภายใน ~1 วินาที และเข้าเมนูของเครื่อง (ไม่มีปุ่ม "ดำเนินการต่อ")
ไม่ผ่าน: ไม่พบอุปกรณ์ / เชื่อมต่อไม่สำเร็จ / ยืนยันสิทธิ์ไม่ผ่าน / **เครื่องของวอร์ดอื่น** → ข้อความบอกเหตุและทางแก้ + ปุ่ม "แตะ NFC อีกครั้ง"
ไม่มีหน้ากรอกรหัส pairing

### 2.4 เมนูของเครื่อง
- หัว: ชื่อเครื่อง, SN · วอร์ด
- การ์ด: ชิปสถานะ, อุณหภูมิ + เวลาที่วัด, แบต %, กล่องที่ติด, ทริปเริ่มโดย, "สด · ข้อมูลจากอุปกรณ์ผ่าน Bluetooth"
- **ดูข้อมูลเพิ่มเติม ▾** (พับไว้): อุณหภูมิละเอียด 2 ตำแหน่ง, แรงดันแบต mV, แหล่งไฟ, ทริป, แจ้งเตือนค้าง, ทริปรอส่ง, ที่มาของเวลา, ตำแหน่ง, พื้นที่ใช้ไป %, Wi-Fi ที่กล่องต่ออยู่
- เมนู: **เริ่ม / จบทริป** · **ตั้งค่าอุปกรณ์** · **ส่งข้อมูล** (badge จำนวนรอส่ง) · ปุ่มตัดการเชื่อมต่อ

### 2.5 เริ่มทริป (เครื่องเดียว) — หน้าเดียว กดครั้งเดียว
ในหน้า "เริ่ม / จบทริป" เมื่อไม่มีทริปทำงาน แสดงฟอร์มเริ่มทริปทันที ไม่มีหลายขั้น:
- **ต่ำสุด / สูงสุด** กรอกไว้ให้แล้ว: ใช้ค่าของทริปล่าสุดของเครื่องนั้น ถ้าไม่มีใช้ 2.0–8.0°C (ต่ำสุด < สูงสุด, −40 ถึง 100°C, เตือนถ้าต่ำกว่า 0°C เพราะ MAX6675 ไม่ยืนยันค่าติดลบ)
- **กล่องที่ติด** ช่องเดียว ไม่บังคับ (ข้อมูลของแอป)
- บรรทัดเล็ก: รอบบันทึกและเวลาก่อนเตือนของเครื่อง (อ่านอย่างเดียว เปลี่ยนที่ตั้งค่าอุปกรณ์)
- **ตรวจความพร้อมอัตโนมัติ** (แบต, หัววัด, พื้นที่) ผ่าน = บรรทัดสีเขียว "พร้อม · แบต 86% · …" ไม่ผ่าน = กล่องสีแดงบอกเหตุและทางแก้ และปิดปุ่ม
- ปุ่มเดียว **เริ่มทริป 2.0–8.0°C** (แสดงช่วงบนปุ่ม) ล็อกระหว่างรอ ทริปเริ่มเมื่อกล่องตอบ `ok` เท่านั้น แล้วหน้าเปลี่ยนเป็น "ระหว่างทริป" เอง ถ้ากล่องตั้งนาฬิกาใหม่ (`clock.adjusted`) แจ้งผู้ใช้
- BLE หลุดหลังส่งคำสั่ง: "ไม่ได้รับการยืนยันจากอุปกรณ์" + **เชื่อมต่อและลองอีกครั้ง** (ส่ง `id` เดิม ได้ทริปเดิม) หรือยกเลิก ระหว่างนี้แอปไม่แสดงว่าทริปเริ่มแล้ว

จำนวนการกด: เปิดเมนู "เริ่ม / จบทริป" → กด **เริ่มทริป** (แก้ช่วงหรือใส่กล่องที่ติดเฉพาะเมื่อต้องการ)
ไม่มีอินเทอร์เน็ตก็เริ่มได้ (สั่งผ่าน BLE)

### 2.6 เริ่มทริปหลายเครื่อง
1. ตั้งช่วงอุณหภูมิครั้งเดียว
2. แตะ NFC ทีละเครื่อง: แต่ละครั้งแอป เชื่อมต่อ → ยืนยันสิทธิ์ → ตรวจความพร้อม → `START_TRIP` → **ตัดการเชื่อมต่อ** แล้วพร้อมแตะเครื่องถัดไป
3. ผลรายเครื่อง: **เริ่มทริปแล้ว** (ระบุกล่องที่ติดได้ในแถว) · **ข้าม** (มีทริปอยู่แล้ว ไม่เริ่มซ้ำ) · **ไม่สำเร็จ** + เหตุผล (แบตต่ำ, ไม่พบหัววัด, วอร์ดอื่น, NFC/BLE ล้มเหลว) + "แตะเครื่องนี้อีกครั้ง" · **ไม่ทราบผล** (BLE หลุดหลังส่งคำสั่ง แตะซ้ำแล้วส่ง `id` เดิม ได้ทริปเดิม)
4. ตัวนับ เริ่มแล้ว / ไม่สำเร็จ / ข้าม และปุ่มเสร็จสิ้น

เลือกแบบ "แตะแล้วเริ่มทีละเครื่อง" เพราะหนึ่งการแตะได้หนึ่ง session และกล่องเปิดรับ BLE ~60 วินาที ไม่ต้องค้าง BLE หลายเครื่องพร้อมกัน

### 2.7 ระหว่างทริป
- เริ่มเมื่อ / เริ่มโดย / ผ่านไปแล้ว
- อุณหภูมิล่าสุด + เวลาที่วัด + อยู่ในช่วง / นอกช่วง
- ช่วงที่อนุญาต, ต่ำสุด / สูงสุดที่บันทึก, จำนวนแถวในเครื่อง + รอบบันทึก, แบต, ตำแหน่ง (ล่าสุด / เก่า / ยังไม่พบ)
- กราฟพร้อมแถบช่วงที่อนุญาต: "อ่านผ่าน Bluetooth เพื่อแสดงในแอปเท่านั้น ข้อมูลเต็มทริปส่ง server หลังจบทริป"
- เหตุการณ์ (เริ่ม, แจ้งเตือน, รับทราบโดยใคร, กลับสู่ปกติ)
- แบนเนอร์แจ้งเตือนสีแดง + **รับทราบการแจ้งเตือน** — รับทราบแล้วแบนเนอร์ยังอยู่ "รับทราบแล้วโดย X แต่ปัญหายังไม่หาย" ไม่ลบประวัติ
- ปุ่ม **จบทริป** ติดล่างจอ

### 2.8 จบทริป
สรุป → เลือก **จบทริป** (เก็บไว้รอส่ง) หรือ **จบทริปและส่งข้อมูล** → ยืนยัน → ผล
- จบอย่างเดียว: "อุปกรณ์หยุดบันทึกแล้ว · รอส่ง" + เริ่มโดย/จบโดย + ปุ่มส่งตอนนี้
- จบและส่ง: ไปหน้าความคืบหน้าการส่ง
- BLE หลุดก่อนกล่องตอบ: **ห้ามแสดงว่าจบแล้ว** → "ยังไม่ได้รับการยืนยันจากอุปกรณ์" + เชื่อมต่อแล้วลองอีกครั้ง (ส่ง `id` เดิม)

### 2.9 ตั้งค่าอุปกรณ์
แสดงค่าปัจจุบันก่อนแก้ → แก้ไขค่า → บันทึก n ค่า / ยกเลิก → ผลรายค่า (บันทึกแล้ว / ยังไม่ได้บันทึก + เหตุผล) ไม่ใช้ข้อความสำเร็จรวมเมื่อยังมีค่าที่ผิด
ทุกค่าในตาราง "ค่าที่แอป / server ตั้งได้" ของ `device-settings.md` แสดงค่าเริ่มต้นและช่วงตามเอกสาร แปลงหน่วยในจอ (วินาที → นาที, 0.01°C → °C) ส่งกล่องเป็นหน่วยเดิม:

| กลุ่ม | ค่า |
|---|---|
| การบันทึกและอุณหภูมิ | `sample_period_s` 🔒, `temp_adj_c100` 🔒 |
| การแจ้งเตือน | `alarm_dwell_s` 🔒, `alarm_hyst_c10` 🔒 (มีคำอธิบาย hysteresis) |
| ตำแหน่งและเวลา | `gnss_period_s`, `tz_offset_min` (ค่าเริ่มต้น UTC+7) |
| ไฟและเสียง | `buzzer_enabled`, `led_front_pct`, `led_bright_pct`, `led_status_s` |
| พลังงานและการขยับ | `idle_wake_s`, `accel_wake_ths` |
| เครือข่ายขั้นสูง (พับไว้) | `upload_period_s` ("รอบส่งผ่าน Wi-Fi ของอุปกรณ์ ไม่เกี่ยวกับการส่งผ่านมือถือ"), `usb_drive`, Wi-Fi ที่ต่ออยู่ตอนนี้, Wi-Fi 5 ช่อง, `ota_base` (อ่านอย่างเดียว), "MQTT ตั้งจากสาย USB เท่านั้น" |
| ข้อมูลอุปกรณ์ (อ่านอย่างเดียว) | ชื่อ, SN, firmware, hardware, protocol, BLE MAC, Wi-Fi MAC, `server_rev`, `tap_test`, `rx_show` |

🔒 = ระหว่างทริปเป็นอ่านอย่างเดียว + "แก้ไขได้หลังจบทริป" (ใช้ `trip_locked` จาก event `SETTINGS`)
ใต้หัวแสดง "แก้ไขล่าสุดจากแอปโดย X · เวลา"

**Wi-Fi ช่อง N**: เพิ่ม/แก้/ลบทีละช่อง (`ADD_WIFI` / `EDIT_WIFI` / `DEL_WIFI`) · DHCP หรือ IP คงที่ (ตรวจรูปแบบ IP, gateway ต้องอยู่วงเดียวกับ IP) · ไม่แสดงรหัสผ่านเดิม เว้นว่าง = ใช้รหัสเดิม · เครือข่ายใหม่หรือเปลี่ยนชื่อต้องใส่รหัสผ่าน (หรือติ๊กเครือข่ายเปิด)

### 2.10 ส่งข้อมูล
- แถบเส้นทาง อุปกรณ์ → Bluetooth → แอป → อินเทอร์เน็ต → Server
- ตัวกรอง ทั้งหมด / รอส่ง / ส่งแล้ว · เลือกทีละทริป หลายทริป หรือทั้งหมดที่รอส่ง
- แถวทริป: ชื่อ/กล่องที่ติด, ทริปที่ N · วันที่, เวลาเริ่ม–จบ, เริ่มโดย/จบโดย, ระยะเวลา, จำนวนแถว, สถานะ
- ทริปที่กำลังบันทึกเห็นได้แต่เลือกไม่ได้ + "ส่งข้อมูลเต็มทริปได้หลังจบทริป"
- ปุ่ม **ส่งข้อมูลที่เลือก (n ทริป)** → ทำ**ทีละทริป** 5 ขั้น:

| ขั้น | คำสั่ง / งาน | ถ้าล้มเหลว |
|---|---|---|
| 1 รับข้อมูลจากอุปกรณ์ผ่าน Bluetooth | `READ_LOG_CHUNK` ทีละ 16 แถวจน `next` = null | เก็บแถวที่ได้ตาม `seq` · "เชื่อมต่อเพื่อรับต่อ" รับต่อจาก `seq` ถัดไป |
| 2 เตรียมไฟล์ CSV ในแอป | `TRIP_<SN>_<YYMMDDhhmm>.csv` ตาม ble-protocol ข้อ 6 | — |
| 3 ส่งขึ้น server | อินเทอร์เน็ตของมือถือ | ไม่มีเน็ต: "รับเข้าแอปครบแล้ว · รออินเทอร์เน็ต" อยู่ในคิวแอป ส่งเองเมื่อมีเน็ต |
| 4 รอ server ยืนยันว่าเก็บแล้ว | คำตอบของ server | "ส่ง Server ไม่สำเร็จ" ไฟล์ยังอยู่ในแอป · ลองส่งใหม่ (ไม่ต้องรับจากกล่องอีก) |
| 5 แจ้งอุปกรณ์ว่าส่งสำเร็จ | `MARK_DELIVERED` **หลัง server ยืนยันเท่านั้น** | "Server รับแล้ว รอยืนยันกับอุปกรณ์" · เชื่อมต่อแล้วยืนยันอีกครั้ง |

แสดง "รับเข้าแอปครบแล้ว" แยกจาก "ส่งถึง Server สำเร็จแล้ว" เสมอ · หลายทริปสำเร็จบางส่วน → ผลรายทริป + "ลองใหม่เฉพาะรายการที่ค้าง"
การส่งไม่ลบทริปในกล่อง · ลองใหม่ไม่สร้างข้อมูลซ้ำ (server กรองด้วย `(trip_id, seq)`)

## 3. Mapping การกระทำ → คำสั่ง BLE

| การกระทำ | คำสั่ง | หมายเหตุ |
|---|---|---|
| แตะ NFC | NDEF `{sn, ble, key}` | หากล่องด้วยชื่อประกาศ (SN) บน iOS |
| ยืนยันสิทธิ์ | `GET_INFO` → `AUTH` (`proof` = HMAC-SHA256(key, nonce)) | หลุดแล้วต้องแตะใหม่ |
| การ์ดเครื่อง / ระหว่างทริป | `GET_STATUS` + STATUS notify, EVENT | |
| ตรวจความพร้อม | `GET_STATUS` (+ `GET_STORAGE_STATUS`, `SELF_TEST` ถ้าต้องการ) | เกณฑ์แบต = `batt_trip_mv` |
| เริ่มทริป | `START_TRIP` `{low, high, utc}` | ไม่ส่ง hyst/dwell แล้ว |
| รับทราบแจ้งเตือน | `ACK_ALARM` | |
| จบทริป | `STOP_TRIP` | |
| กราฟระหว่างทริป | `READ_LOG_CHUNK` ของทริปที่กำลังบันทึก | firmware อ่านได้ (ไม่ได้กันทริปที่ active) อ่านต่อจาก `seq` ล่าสุดที่มี |
| อ่านค่าตั้ง | event `SETTINGS` / `GET_SETTINGS` | `editable`, `trip_locked`, `network` หลัง AUTH |
| บันทึกค่าตั้ง | `APPLY_CONFIG` `{config:{…}}` | ผลรายค่า `applied` / `errors` |
| Wi-Fi | `ADD_WIFI` / `EDIT_WIFI` / `DEL_WIFI` | |
| Wi-Fi ที่ต่ออยู่ | event `WIFI` | |
| รายการทริป | `LIST_TRIPS` + `GET_TRIP_SUMMARY` ต่อทริป | summary ให้ `start_utc`, `stop_utc`, `low`, `high`, `samples`, `min`, `max`, `alarms` |
| ส่งข้อมูล | `READ_LOG_CHUNK` → CSV → server → `MARK_DELIVERED` | |

**ทุกคำสั่งที่เปลี่ยนค่า**: เมื่อหมดเวลาหรือ BLE หลุด ให้ลองใหม่ด้วย **`id` เดิม** (กล่องตอบคำตอบเดิม ไม่ทำซ้ำ)

## 5. ข้อความผิดพลาด

| จากกล่อง | ข้อความ | ทางแก้ที่แสดง |
|---|---|---|
| `ALREADY_ACTIVE` | อุปกรณ์มีทริปกำลังทำงานอยู่แล้ว | จบทริปเดิมก่อน |
| `BATTERY_LOW` | แบตเตอรี่ต่ำเกินกว่าจะเริ่มทริป | ชาร์จกล่องแล้วลองใหม่ |
| `LOG_FULL` | พื้นที่บันทึกในอุปกรณ์เต็ม | ส่งข้อมูลทริปเก่าที่รอส่ง |
| `NOT_ACTIVE` | อุปกรณ์ไม่มีทริปที่กำลังทำงาน | ตรวจรายการรอส่ง (หลัง "ไม่ทราบผล" ของการจบทริป ให้ถือว่าจบแล้วถ้าทริปอยู่ใน `LIST_TRIPS`) |
| `NOT_AUTHORIZED` | ยืนยันสิทธิ์ไม่ผ่าน | แตะ NFC อีกครั้ง |
| `EXISTS` / `FULL` / `NOT_FOUND` (Wi-Fi) | มีเครือข่ายนี้แล้ว / ครบ 5 ช่อง / ช่องว่างอยู่ | ตามข้อความ |
| BLE หลุดหลังส่งคำสั่ง | ไม่ได้รับการยืนยันจากอุปกรณ์ | เชื่อมต่อแล้วลองอีกครั้ง (`id` เดิม) |

## 6. ฝั่งเครื่อง (firmware) ต้องแก้การส่งข้อมูลไหม

ตรวจกับ firmware `0.7.0-dev.51` (branch `firmware/p7-power`, `firmware/src/rpc.cpp`):

**ไม่ต้องแก้** — ทุกอย่างที่ demo ใช้มีใน firmware แล้ว:
`START_TRIP` (มี `utc`, จำ `id` ใน flash), `STOP_TRIP`, `ACK_ALARM`, `LIST_TRIPS`, `GET_TRIP_SUMMARY`,
`READ_LOG_CHUNK` (มี `from` จึงรับต่อจากจุดที่หลุดได้ และอ่านทริปที่กำลังบันทึกได้), `MARK_DELIVERED`,
`APPLY_CONFIG`, `GET_SETTINGS`, `GET_NETWORK`, `ADD_WIFI` / `EDIT_WIFI` / `DEL_WIFI`, event `SETTINGS` และ `WIFI`
และ id เดิม = คำตอบเดิม การเริ่มหลายเครื่อง การเก็บคิวในแอป และการส่งทีละทริปทำในแอปทั้งหมด

**เอกสารควรปรับให้ตรง firmware** (ไม่ต้องแก้โค้ด):
- ตาราง error ใน `ble-protocol.md` ยังไม่มี `BATTERY_LOW` (firmware ตอบเมื่อแบตต่ำกว่า `batt_trip_mv` และไม่ได้เสียบไฟ)
- `GET_TRIP_SUMMARY` ตอบ `start_utc`, `stop_utc`, `low`, `high`, `hyst`, `dwell_s` ด้วย แต่เอกสารยังไม่ระบุ
- `START_TRIP` รับ `low` ≥ −40 และ `high` ≤ 100°C ถ้าเกินได้ `BAD_ARGS` (ยังไม่อยู่ในเอกสาร)
- วันที่/เวอร์ชันหัวไฟล์ `ble-protocol.md` (7 ต.ค.) และ `device-settings.md` (5 ต.ค.) เก่ากว่าเนื้อหา (9 ต.ค.)

**แนะนำ (ไม่บังคับ) ถ้าทีม firmware ทำได้:**
1. `LIST_TRIPS` ใส่ `start_utc` / `stop_utc` / `rows` มาด้วย — ตอนนี้หน้า "ส่งข้อมูล" ต้องเรียก `GET_TRIP_SUMMARY` ทีละทริปเพื่อแสดงเวลาและระยะเวลา (สูงสุด 64 ครั้ง)
2. จำ `id` ของ `STOP_TRIP` ใน flash แบบเดียวกับ `START_TRIP` — ตอนนี้จำแค่ใน RAM (8 รายการ) ถ้ากล่องรีเซ็ตระหว่าง "ไม่ทราบผล" แอปจะได้ `NOT_ACTIVE` แทนคำตอบเดิม (แอปรับมือได้ด้วยการเช็ก `LIST_TRIPS`)

**ต้องแก้ firmware เฉพาะถ้าตัดสินใจแบบนี้:**
- อยากให้ผู้ใช้หรือกล่องที่ติดอยู่ในข้อมูลของกล่องเอง (ใน log, CSV บนไดรฟ์ USB หรือบนจอ e-paper) — หัว trip มีขนาดตายตัว ต้องเปลี่ยน record format · **แนะนำเก็บที่ server ผูกกับ `trip_id` แทน ไม่ต้องแก้ firmware**
- อยากให้กล่องปฏิเสธมือถือของวอร์ดอื่นเอง — ตอนนี้ใครแตะ NFC ก็ AUTH ได้ · **แนะนำให้แอป/server กันไว้ก่อน**

**พฤติกรรมของกล่องที่แอปต้องรู้ (ไม่ต้องแก้):** เลือก "จบทริป" อย่างเดียว หรือแอปส่งไม่สำเร็จ กล่องจะส่งทริปเองทาง Wi-Fi เมื่อเจอเครือข่าย ทริปจึงอาจกลายเป็น "ส่งแล้ว" เองใน `LIST_TRIPS` และ server ได้ทริปเดียวกันสองทาง (กรองด้วย `(trip_id, seq)`)

## 7. ฝั่ง server ต้องทำ

1. **API รับไฟล์ CSV จากแอป** และคำตอบ "เก็บครบแล้ว" ที่แอปใช้ตัดสินก่อนเรียก `MARK_DELIVERED` (ยังรอตกลงตาม `trip-data-flow.md`)
2. **ทะเบียนเครื่อง** SN → ลูกค้า → วอร์ด
3. **ผู้ใช้และการเข้าสู่ระบบ** ผู้ใช้สังกัดวอร์ด
4. **ข้อมูลของแอปต่อทริป**: กล่องที่ติด, หมายเหตุ, ผู้เริ่ม/จบ, ผู้รับทราบแจ้งเตือน, ผู้ส่ง — แชร์ข้ามมือถือในวอร์ด
5. (ถ้าต้องการ) **API สถานะล่าสุดของเครื่องในวอร์ด** จาก `status` ที่กล่องส่งทาง MQTT เพื่อให้รายการเครื่องเป็นค่าสด
