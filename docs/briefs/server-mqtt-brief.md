# mCOLD — สิ่งที่ฝั่ง Server ต้องทำ (MQTT)

เอกสารนี้สรุปสำหรับทีม server: กล่อง mCOLD ส่งอะไรขึ้นมา, server ต้องตอบอะไรกลับ,
และเรื่องที่ต้องตัดสินใจร่วมกัน ฝั่งกล่องทำเสร็จและเชื่อมต่อ broker ของทีมได้แล้ว
**สิ่งที่ยังขาดคือ ACK จาก server** รายละเอียดเต็มอยู่ใน `firmware/PROTOCOL.md` ข้อ 6

## 1. สิ่งที่ต้องทำ เรียงตามความสำคัญ

| # | เรื่อง | ถ้ายังไม่ทำ |
|---|---|---|
| 1 | **ส่ง ACK** หลังเก็บข้อมูลลงฐานข้อมูลแล้ว (ข้อ 4) | กล่องไม่ลบข้อมูลเลย ส่งชุดเดิมซ้ำ และเว้นระยะการส่งนานขึ้นถึง 4 ชั่วโมง ข้อมูลใหม่ขึ้นช้ามาก |
| 2 | **ACK ให้เร็ว** ภายใน 1–2 วินาที | ทุกวินาทีที่รอคือวิทยุ Wi-Fi เปิดค้างในทุกกล่อง กินแบตโดยตรง |
| 3 | **เก็บแบบไม่ซ้ำ** โดยใช้ (sn, trip, seq) เป็น key | กล่องส่งซ้ำทุกครั้งที่ไม่ได้ ACK ข้อมูลจะซ้ำในฐานข้อมูล |
| 4 | **เปิด TLS (8883) และ login แยกต่อเครื่อง** | ตอนนี้ข้อมูลและรหัสผ่านวิ่งแบบไม่เข้ารหัส และใครมี login เดียวกันก็ปลอม ACK ได้ ทำให้กล่องลบข้อมูลที่ยังไม่ถึง server |
| 5 | ส่ง OTA ตามข้อ 8: publish ชื่อไฟล์แบบ **retain** แล้วลบเมื่อได้ `ok` | กล่องที่ใช้แบตหลับอยู่จะไม่เห็นคำสั่ง |

## 2. การเชื่อมต่อ

- client id = รหัสเครื่อง (`sn`) ตามฉลาก เช่น `mCDV1-L0169-1069-001` (ตัวพิมพ์เล็ก-ใหญ่มีผล)
  กล่องที่ยังไม่ได้ตั้ง SN จากโรงงานจะใช้ชื่อชั่วคราว `MCOLD-xxxx`
- broker และ login ตั้งในเครื่องแต่ละกล่อง ไม่อยู่ใน firmware หรือ git
- แบบเดียวกับ eTEMP: **ที่กล่อง publish อยู่ใต้ `mcold/<sn>/`** และ **ที่กล่อง subscribe
  (server publish) อยู่ใต้ `mcold/v1/<sn>/`** (`v1` คือเวอร์ชันของคำสั่งที่กล่องเข้าใจ)
- สรุปทุก topic อยู่ที่ `docs/mqtt-topics.md`

| Topic | ทิศทาง | QoS | Retained | เนื้อหา |
|---|---|---|---|---|
| `mcold/<sn>/rec` | กล่อง → server | 1 | ไม่ | ชุด record (ข้อ 3) |
| `mcold/v1/<sn>/ack` | **server → กล่อง** | 1 | ไม่ | `{"trip":T,"upto":S}` (ข้อ 4) |
| `mcold/<sn>/status` | กล่อง → server | 0 | ใช่ | สถานะล่าสุด (JSON เดียวกับ `GET_STATUS`) |
| `mcold/<sn>/online` | กล่อง → server | 1 | ใช่ | `"1"` ตอนเชื่อมต่อ, `"0"` ตอนจบรอบหรือหลุด (last will) |

รับข้อมูลทุกกล่องได้ด้วยการ subscribe `mcold/+/rec`

## 3. ข้อมูลที่กล่องส่งขึ้นมา

ทุก record เป็น **แถวเดียวกัน มี column ชุดเดียวกัน** ไม่ว่าจะเป็น sample หรือ event
(ตกลงกันเมื่อ 5 ต.ค.) แต่ละแถวมีสถานะของกล่อง ณ ตอนนั้นครบ server เก็บลงตารางเดียวได้เลย
และเป็น column ชุดเดียวกับไฟล์ CSV ที่คนเปิดดู

```
{"sn":"mCDV1-L0169-1069-001","trip":11,"schema":3,"from":0,"to":15,
 "rows":[
  {"trip":11,"seq":1,"sn":"mCDV1-L0169-1069-001","timestamp":"02:47:27 05/10/2026",
   "utc":1791143247,"event":"SAMPLE","temp":4.25,"tempmin":2,"tempmax":8,"alarm":"",
   "timeok":true,"gnssstate":"last","latitude":13.7563,"longitude":100.5018,"motion":0,
   "battery":97,"internet":"online","detail":""},
  {"trip":11,"seq":2,"sn":"mCDV1-L0169-1069-001","timestamp":"02:47:28 05/10/2026",
   "utc":1791143248,"event":"ALARM_HIGH","temp":8.5,"tempmin":2,"tempmax":8,"alarm":"HIGH",
   ...}, ...]}
```

- ชุดละไม่เกิน 16 แถวของ trip เดียว เรียงตาม `seq`
- **key ของแต่ละแถวคือ (sn, trip, seq)**

| column | ความหมาย |
|---|---|
| `trip` | เลข trip ที่กล่องสร้างเอง (ไม่ซ้ำเมื่อคู่กับ `sn`) |
| `seq` | ลำดับแถวใน trip เริ่มที่ 0 |
| `sn` | serial number ของกล่อง |
| `timestamp` | เวลาไทย `hh:mm:ss DD/MM/YYYY` |
| `utc` | เวลาเดียวกันเป็น Unix seconds สำหรับเรียงลำดับ |
| `event` | แถวนี้คืออะไร (ตารางถัดไป) |
| `temp` | อุณหภูมิ °C; `null` = probe อ่านไม่ได้ |
| `tempmin` / `tempmax` | ช่วง alarm ของ trip นี้ |
| `alarm` | alarm ที่ค้างอยู่ `HIGH`, `LOW`, `PROBE`, `BATTERY` คั่นด้วย `|`; ว่าง = ไม่มี |
| `timeok` | `false` = กล่องไม่รู้เวลาตอนนั้น (`timestamp`/`utc` เป็น `null` และมี `boot`, `up_s` ไว้เรียงลำดับ) |
| `gnssstate` | `fix` = ตำแหน่งใหม่, `last` = ตำแหน่งเก่า, `none` = ไม่มี |
| `latitude` / `longitude` | องศา; `null` เมื่อ `none` |
| `motion` | จำนวนครั้งที่ขยับตั้งแต่แถวก่อน |
| `battery` | แบต % |
| `internet` | ผลการส่งรอบล่าสุด: `online`, `wifi_only` (ต่อ Wi-Fi ได้แต่ไม่ถึง server), `offline` |
| `detail` | รายละเอียดของ event (ส่วนใหญ่ว่าง) |

| `event` | เกิดเมื่อ | `detail` |
|---|---|---|
| `TRIP_START` / `TRIP_STOP` | เริ่ม / จบ trip | |
| `SAMPLE` | ทุกรอบบันทึก (ค่าเริ่มต้น 5 นาที) | |
| `ALARM_HIGH` / `ALARM_LOW` | อุณหภูมิเกิน `tempmax` / ต่ำกว่า `tempmin` นานกว่าเวลาที่ตั้ง | |
| `ALARM_PROBE` | อ่านอุณหภูมิไม่ได้เกิน 1 นาที | |
| `BATTERY_LOW` | แบตต่ำกว่า 15% | % |
| `ALARM_CLEAR` | alarm หาย | ชนิด |
| `ALARM_ACK` | มีคนกดรับทราบ | alarm ที่รับทราบ |
| `PROBE_FAULT` / `PROBE_OK` | probe หลุด / กลับมา | สาเหตุ |
| `USB_IN` / `USB_OUT` | เสียบ / ถอดไฟ | |
| `POWER_ON` | เครื่องรีเซ็ตแล้วทำ trip ต่อ | สาเหตุการรีเซ็ต |
| `POWER_OFF` | แบตหมด เครื่องตัดตัวเอง | mV |
| `TIME_SET` | มีการตั้งเวลา | เวลาก่อนตั้ง |
| `DATA_LOST` | trip เก่าถูกลบเพราะพื้นที่เต็ม | เลข trip |
| `SHOCK` | สำรองไว้: กระแทกแรงเกินเกณฑ์ (ยังไม่ได้ตั้งเกณฑ์) | |

การขยับธรรมดาไม่เป็นแถว นับรวมไว้ใน `motion`

## 4. ACK — สิ่งที่ server ต้องตอบ

1. เก็บแถวของชุดนั้นลงฐานข้อมูลให้เรียบร้อย **ใช้ (sn, trip, seq) เป็น key**
   record ที่มาซ้ำต้องเก็บครั้งเดียว
2. จากนั้น publish ไปที่ `mcold/v1/<sn>/ack`
   ```
   {"trip":8,"upto":15}
   ```
   แปลว่า **record ของ trip 8 ตั้งแต่ seq 0 ถึง 15 เก็บครบแล้ว** ต้องต่อเนื่อง
   ห้ามตอบ `upto` ถ้ายังมี seq ที่น้อยกว่านั้นขาดอยู่

- **PUBACK ของ MQTT ไม่นับเป็น ACK** เพราะบอกแค่ว่า broker ได้รับ ไม่ใช่ว่า server เก็บแล้ว
- กล่องตรวจ ACK ทุกครั้ง: ถ้าเป็น trip ที่ไม่มี หรือ `upto` เกินข้อมูลที่มี จะไม่รับ
- ACK ซ้ำหรือมาช้าไม่เสียหาย เพราะค่านี้เดินหน้าอย่างเดียว

## 5. จังหวะการส่งเมื่อกล่องใช้แบต

กล่องหลับระหว่างรอบเพื่อประหยัดแบต และ Wi-Fi ปิดอยู่ จะเชื่อมต่อเป็น **รอบสั้นๆ** ทุก 5 นาที
เมื่อมีข้อมูลรอส่ง:

1. เปิด Wi-Fi → เชื่อม broker → ส่ง `status` → ส่งชุด record
2. **รอ ACK ชุดละไม่เกิน 10 วินาที** ได้ ACK แล้วส่งชุดถัดไป
3. จบรอบ: ส่ง `"0"` ที่ `online` แล้วตัดการเชื่อมต่อ

| สถานการณ์ | กล่องทำอะไร |
|---|---|
| server ACK ทันเวลา | รอบถัดไปตามปกติใน 5 นาที |
| ไม่ได้ ACK ในรอบนั้น | เว้นระยะรอบถัดไปเป็น 10, 20, 40 … นาที สูงสุด 4 ชั่วโมง |
| ACK มาหลังจบรอบแล้ว | ACK นั้นหายไป (กล่องใช้ clean session) รอบหน้ากล่องส่งชุดเดิมซ้ำ server แค่ ACK อีกครั้ง |

**สรุปสำหรับ server:**
- ACK ภายใน 1–2 วินาที ทำให้แต่ละรอบใช้เวลาราว 5 วินาที
- ดูว่ากล่องยังติดต่อได้จากเวลาของ `status` ล่าสุด ไม่ใช่จาก `online` เพราะกล่องที่ใช้แบตจะเป็น `"0"` เกือบตลอดเวลาและถือว่าปกติ
- ตอนเสียบสาย USB กล่องเชื่อมต่อค้างไว้ตลอด ใช้ทดสอบฝั่ง server ได้สะดวก

## 6. ความปลอดภัย — ขอให้เปิดก่อนใช้งานจริง

- **TLS ที่พอร์ต 8883** พร้อม certificate ของ server ที่กล่องตรวจสอบได้
- **login แยกต่อเครื่อง** (หรือ client certificate)
- **ACL:** แต่ละกล่อง publish ได้เฉพาะ `mcold/<sn>/rec`, `status`, `online`, `ota/state` ของตัวเอง
  และ subscribe ได้เฉพาะ `mcold/v1/<sn>/ack`, `firmware` ของตัวเอง ส่วน `ack` และ `firmware` ให้ publish ได้เฉพาะ server

เหตุผล: ACK คือคำสั่งให้กล่อง "ลบข้อมูลได้" ถ้าใครปลอม ACK ได้ ข้อมูลที่ยังไม่ถึง server จะหายถาวร

## 7. คำถามที่ต้องการคำตอบ

1. ยอมรับรูปแบบ topic และ ACK ตามนี้ไหม หรืออยากปรับตรงไหน
2. เปิด TLS 8883 และ login แยกเครื่องได้เมื่อไหร่
3. ~~OTA แบบไหน~~ ตกลงแล้ว: แบบเดียวกับ eTEMP (ข้อ 8)
4. ใครเป็นผู้ติดต่อฝั่ง server สำหรับทดสอบร่วมกัน

## 8. อัปเดต firmware (OTA)

ทำแบบเดียวกับ eTEMP: server ส่ง**แค่ชื่อไฟล์** กล่องดาวน์โหลดเองจาก file server
(`https://drive.siamatic.co.th/media/firmwares/<ชื่อไฟล์>`) ทดสอบผ่านแล้ว 2026-10-04

1. วางไฟล์ `mCOLD_<เวอร์ชัน>.bin` ที่ทีม firmware ส่งให้ ไว้ในโฟลเดอร์ firmwares
2. publish ชื่อไฟล์ไปที่ `mcold/v1/<sn>/firmware` แบบ **retain** เช่น `mCOLD_0.7.1.bin`
   (กล่องที่ใช้แบตหลับอยู่เกือบตลอด จะเห็นคำสั่งตอนตื่นมาส่งข้อมูลรอบถัดไป)
3. ดูผลที่ `mcold/<sn>/ota/state` (retain):

| state | ความหมาย |
|---|---|
| `downloading` + `pct` | กำลังดาวน์โหลด |
| `rebooting` | ติดตั้งเสร็จ กำลังรีสตาร์ท |
| `ok` | เวอร์ชันใหม่ทำงานและต่อ broker ได้แล้ว |
| `failed` + `reason` | ไม่ติดตั้ง (ไฟล์ไม่มี, ลายเซ็นไม่ผ่าน, ไม่ใช่ firmware mCOLD) |
| `deferred` + `reason` | รอก่อน: มี trip อยู่ (`trip`) หรือแบตต่ำกว่า 30% (`battery`) แล้วทำเองเมื่อพร้อม |
| `rolled_back` | เวอร์ชันใหม่ต่อ broker ไม่ได้ใน 3 นาที กล่องถอยกลับเวอร์ชันเดิมเอง |
| `skipped` | เวอร์ชันไม่ใหม่กว่าที่มีอยู่ |

4. ได้ `ok` แล้ว ให้ลบ retained message (publish ค่าว่างแบบ retain ไปที่ topic เดิม)

server ไม่ต้องตรวจอะไร: กล่องตรวจเองทั้งหมด (โครงการ, เวอร์ชัน, SHA-256 และ**ลายเซ็น**)
ไฟล์ที่ไม่ได้เซ็นด้วย key ของทีม firmware จะถูกปฏิเสธ แม้จะวางอยู่ในโฟลเดอร์เดียวกัน
เวอร์ชันที่กล่องใช้อยู่ดูได้จาก `status` → `fw.ver`
